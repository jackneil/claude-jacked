Goal

jacked assumes every account has a 5-hour window. On 2026-10-30 Anthropic renamed Max 5x to Max and Max 20x to Ultra, and removed the 5-hour limit for verified Ultra accounts (weekly limits unchanged, plus a separate weekly Fable limit). ChatGPT Pro also has no 5-hour limit in Codex. This change moves "which windows does this account type have, what is it called, and how long is each window" into a data file that ships with each jacked release (jacked/data/usage_plans.json), so the next provider change is a data edit, and makes every consumer read windows through it. It also fixes the missing week-elapsed marker on the Fable row, for the whole class of model-scoped bars.

Precedence rule: the provider's live payload is the truth for one account right now; the catalog says what each plan is expected to have, decides how to read silence for that plan, names the plan, and gives window lengths. When the two disagree, jacked follows the payload where it is explicit and logs a catalog-drift warning once per shape.

Evidence

  • Anthropic help center, "What is the Ultra plan?" (support.claude.com/en/articles/17728952): "The Max 20x plan is now called the Ultra plan." "Verified Ultra accounts don't have a five-hour limit." "If your account isn't verified yet, a temporary limit applies." "If you don't see a Current session bar, your account is verified." Separate weekly Fable limit.
  • Help center, "How do usage and length limits work?" (articles/11647753): weekly limits reset at a fixed time per account.
  • Live payloads on this machine (2026-11-01): all 5 default_claude_max_20x accounts return five_hour: null and a limits[] with only weekly_all + weekly_scoped (Fable). Max 5x and Team return kind: "session". Profiles carry organization.plan_display_name: "Ultra" on the 20x rows.
  • Codex Pro payload: one primary window, windowDurationMins: 10080, secondary: null.
  • Keeper log: pings jumped from ~28/day to ~150/day on 2026-10-31; 290 pings at the 5 Ultra accounts since 10-30, each ping_ok_no_window, backoff stuck at 600 s ("1 consecutive failures" every time).
  • Dashboard before: Ultra cards show "5h limit 0% retry due" and "Max subscription (20x tier)"; Fable rows have no marker.

Spec: acceptance criteria and non-goals

User-facing goal

Every surface shows the windows an account really has, under the plan's current name, with a week-elapsed marker on every bar; jacked stops spending pings and quota on windows that cannot exist; a future provider change is a catalog edit in a release.

Acceptance criteria

  1. AC1 Catalog. jacked/data/usage_plans.json ships in the wheel, has version, verified_at, per-plan sources, window lengths, and plan entries for Claude (Ultra, Max, Team, Pro, Enterprise, Free, unknown-tier Max) and Codex (Pro, Plus). A missing or malformed file degrades to built-in defaults with a WARNING, never a crash. A newer version warns and reads best-effort.
  2. AC2 Resolution. Given a verified Ultra row (payload without a session limit), the resolver returns session state absent; an unverified Ultra (payload with a session limit) returns present + temporary; a Max or Team row returns present whether or not a window is open; Codex Pro returns absent; a Codex partial read returns unknown.
  3. AC3 Labels. Plan label precedence: provider plan_display_name, then catalog label, then the raw subscription type. Ultra rows read "Ultra" (hover "Formerly Max 20x"), Max 5x rows read "Max", Team reads "Team". No regex on the tier multiplier remains.
  4. AC4 API. GET /api/auth/accounts and every WebSocket account payload carry plan and windows; usage.five_hour is null (not 0) for an absent window; every per-model and binding entry carries window_seconds.
  5. AC5 Marker. Every usage bar that has a future reset shows the white elapsed marker, including the Fable binding row on the card, the per-model details list, the WebSocket live refresh, and the menu-bar panel. A source-scan test fails if any renderUsageBar call passes a literal null elapsed fraction.
  6. AC6 Display. An absent 5h window renders an empty track, "none", and "not on Ultra" (hover: the catalog note); the panel caption reads "not on Ultra"; the tray pill reads "-·33%"; jacked usage shows "none" in the 5h columns and the plan label.
  7. AC7 Keeper. The keeper never pings for a 5h window on an account whose session is absent (skip reason no_session_window); it still pings for a turned-over weekly window, and a 7d-only header reading is stored for such accounts; a ping_ok_no_window backoff escalates 600, 1200, 2400, 3600 s instead of resetting to 600 s.
  8. AC8 Crashes. "Refresh all usage" and OAuth add/re-auth both succeed for an account whose payload has five_hour: null.
  9. AC9 Decisions. Auto-swap's 5h headroom gate is explicit for absent windows; the 5h critical threshold comes from the catalog (Ultra 95, Max 90, Team 90, Pro/Free/Enterprise/unknown 80, unknown-tier Max 90); poll urgency for a no-session account follows its weekly and model-weekly windows; the burn-rate tracker updates when only 7d moves; the exhaustion banner's recovery time comes from each account's constrained windows and its text names no 5h window.
  10. AC10 Pacing + skill text. jacked usage --json rows add plan, plan_id, session_window, model_limits; the summary adds best_account_worst_window, best_account_worst_window_resets_at, plan_catalog; the pinned fields keep their meaning. chain-of-command rule 7 reads the plan-agnostic fields.
  11. AC11 Aging. A payload that contradicts the catalog (session on a never plan, silence on an always plan, an unlisted tier of a tier-split subscription, a provider plan name that differs from the catalog) logs one WARNING per shape per process and appears in plan.drift and summary.plan_catalog.drift.

Non-goals

  • No new auto-swap departure rule for an account walled on its weekly or Fable limit (filed, see below).
  • No change to the tray pill's color formula (the Fable cap does not tint the pill yet; filed).
  • No user-editable override of the catalog; the catalog changes only with a release.
  • No reading of pace, weekly_scoped_shares, seven_day_breakdown, or the dollar-denominated codename windows.
  • No change to the 5h-window throughput heuristic in auto_swap/burn.py.

Session resolution (evidence order)

  1. The payload reports a session window (a limits[] entry with kind == "session", a five_hour object with a non-null utilization or reset, or a Codex short window): present; temporary on an until_verified plan; drift session_on_never_plan on a never plan (the payload still wins).
  2. The payload is authoritative and silent: absent, except a Claude always plan, which stays present (silence can mean "no window open") with drift session_missing. A Codex always plan reads absent with drift session_missing (Codex lists every window an account has).
  3. The payload is not authoritative, but the row still holds a 5-hour reading or reset (prior evidence): present (temporary on until_verified). A partial read must never erase a live window.
  4. No evidence: never → absent; until_verified or any Codex plan → unknown; Claude always/reported → present (legacy idle reading).

"Authoritative" for Claude: the raw payload has a limits list AND every entry's kind is one jacked knows (session, weekly_all, weekly_scoped). An unknown kind makes the list non-authoritative and is drift unknown_limit_kind, so a renamed session kind can never read as "no 5-hour limit". For Codex: jacked.codex.usage.normalize_rate_limits(raw) gives five_hour.reported and windows_complete (authoritative). unknown counts as having a window for every decision (keeper, headroom, urgency): jacked never skips a window it cannot rule out.

Payload contract

"plan": {
  "id": "ultra",                 // catalog id, or null when no entry matched
  "label": "Ultra",              // provider plan_display_name > catalog label > raw subscription type (Title Case)
  "formerly": "Max 20x",         // or null
  "label_source": "provider",    // provider | catalog | raw
  "drift": [],                   // codes: session_missing, session_on_never_plan, unknown_tier, unknown_limit_kind, renamed
  "catalog_verified_at": "2026-11-01"
}
"windows": {
  "five_hour": {"state": "absent", "temporary": false, "seconds": 18000,
                "note": "Verified Ultra accounts have no 5-hour limit. Weekly limits still apply."},
  "seven_day": {"state": "present", "temporary": false, "seconds": 604800, "note": null}
}
ModelUsage / binding entries: + "window_seconds": 604800

AccountUsage.five_hour: the cached value; when the cached value is null it is 0 only for a Claude account whose session state is present, otherwise null. seven_day keeps today's rule (Codex null stays null, Claude null reads 0). menubar_summary.summarize_account uses the same rule.

Filed, not fixed here

Decisions made (reviewable)

  • Known plans documented to have a 5h limit use always (silence reads as an idle window), so an idle Max is never mistaken for a plan without the limit; drift logs if Anthropic ever drops the window for them.
  • An Ultra row with no authoritative payload and no cached reading is unknown (treated as having a window), and a cached reading keeps a temporary window alive through a partial read: a wrong "absent" would also bypass the headroom gate and pacing, not just one keeper ping (pre-mortem finding).
  • The 5h row stays on every card (empty track, "none", "not on Ultra") instead of disappearing: it states the plan fact, keeps cards in the grid aligned, and keeps the WebSocket child indexing stable.
  • The provider's own plan name wins over the catalog label, so a rename shows up without a release; a mismatch is drift, not an error.
