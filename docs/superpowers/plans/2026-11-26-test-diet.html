Goal

Ship the skill /test-diet for Claude Code and Codex, and the four commands that it uses: jacked tests ledger, jacked tests collect, jacked tests ids and jacked tests covdiff with jacked tests report. A run of the skill makes a repository's test suite smaller and faster on a branch. Each cut has its evidence in a ledger. The run ends with a report and a pull request that a person reviews.

Spec: 2026-11-25-test-diet-design.html, Part 2, "What a run does", "What proves a cut", "Safety rules", and the section "Changes after the plan review". Recorder: 2026-11-26-test-diet-recorder.html.

What this plan is based on

  • The approved spec: the ledger with its marks and kinds, ledger (it refuses a delete row with a missing field) and ids (the IDs before and after a batch against the ledger).
  • The owner's own prune of 2026-11-24 in one of his repositories: evidence for each cut from a read-only agent, a second agent that argues against each cut, a coverage comparison, and a green gate at the end.
  • The owner's answer of 2026-11-26 on the commands that the review added: build collect, covdiff and report; do not build prove, ledger protect or ledger approve as commands. The planted-defect check stays in the skill text as a method. A second agent runs a sample of those checks again. A run never cuts a protected test; the pull request proposes it.
  • The second review of the older skill plan. Its findings that apply to these four commands are in the tasks: the baseline is tied to the tree and the gate command of the ledger; the ledger holds the trees of each batch; the signals of loss are in the skill steps and in the report; the control of the saving has a definition; a dead-target cut and a duplicate cut each have a mechanical check; a proof is tied to the content of its row.

What the checks can and cannot do

A model writes the ledger. No local command can stop a ledger that a model forges. Each check in this plan catches a careless error: a missing field, a cut of a test that failed, a proof for a different row, a removal that no row names, a keeper that does not exist, a saving that is noise. The person who reviews the pull request is the last check. The report puts the evidence of each cut in front of that person.

Global constraints

The global constraints of the recorder plan apply. These are added.

  • The skill text is guidance for a model. No point tables, no regular expressions that give a verdict. A name or a text pattern only nominates a test.
  • The new skill has no <!-- ENGINE --> marker and has disable-model-invocation: true and agents/openai.yaml with the exact content of recorder Task 6.
  • A failing test is never a candidate. A red baseline gives a report only.
  • Slow is not a reason to delete. A slow test gets a speed or a tier row.
  • The ledger and the report hold test IDs, numbers and evidence text. No failure message, no log text, no private value of the machine (recorder rule of private_hits, as product code in jacked/testdiet/privacy.py).

Review focus

  1. A ledger row whose claim is false or stale: a cut of a test that failed in the baseline, a baseline of a different tree or command, a proof that belongs to an older form of the row, a "covered" cut whose keeper is gone after the batch. Expected: ledger or ids refuses each one. Tests in Tasks 1 and 2.
  2. A batch removes a test that no row names, or a consolidation renames tests. Expected: the first fails, the second passes with the map. Tests in Task 2.
  3. A shared fixture change makes every test faster. Expected: the report does not claim a saving against a control that the change touched. Test in Task 3.
  4. The skill starts inside an autonomous run, or on a tree with changes that are not committed. Expected: it stops. The live proof tries both (Task 5).
  5. A test that a rule file protects. Expected: no run cuts it; the pull request lists it as a proposal. Skill text and live proof.

Where a run keeps its filesdocs/test-diet/<date>-<slug>/: ledger.json, proofs/<row key>.patch, report.html. They are part of the pull request of the run.The record of what was retired and why stays in the repository, so that an agent does not write the same test again.
The baselineThe ledger names base_tree, gate_command_sha and baseline_run. The baseline run must be a record of source run with verdict passed, its tree must be base_tree, and its command SHA must be gate_command_sha.A green record of a different tree or command proves nothing about this one.
BatchesThe ledger holds batches: {"1": {"before": TREE, "after": TREE, "before_ref": ID, "after_ref": ID}, ...}. ids writes the entry of a batch when its check passes. The before of batch 1 is base_tree; the before of batch N is the after of batch N-1.Each batch is checked against the tree that it started from.
A proofThe model runs the planted-defect check by the method of the skill and writes the result: proof: {patch, patch_sha, row_digest, subject, keeper, after, ran_at}, with subject, keeper and after each one of "failed", "passed" or null. row_digest is the SHA-256 of the row's id, mark, kind, keeper and renamed_to. No command runs the check.The owner's answer of 2026-11-26. The digest catches a proof that a later edit of the row made stale.
Protected testsA row has protected (the class, or null). ledger verify refuses a delete or a consolidate row with a protected value. The report lists such rows as proposals.A run never cuts a protected test.
A dead-target cutThe row names the dead code in dead_code as path or path::name, and the same batch deletes that code. ids checks in the after tree that the path does not exist or holds no whole-word match of the name.A mechanical check for this kind. A test of code that stays is not a dead-target cut.
A duplicate or a covered cutThe row names a keeper. ids checks that the keeper is in the after side and, when the after side is a run, that it passed.A mechanical check for these kinds.
The control of the savingThe control is each test that is in both runs, in no row, and in a file that the branch did not change. When the branch changed a file of the test tree that is not a test file (for example conftest.py or a setup file), the report says that the control can share that change. The ratio is the sum of the seconds of the control after, divided by the sum before. A change of the touched tests is reported as "not measurable" when its ratio is between the control ratio and 1, or above 1.The second review asked for a definition. The times of two machines or two commands are never compared.

Rules of verify_ledger.

  • A ledger with a delete, consolidate, speed or fix row needs the baseline of the decisions table. If the baseline fails a condition, each such row is a problem.
  • The test of a delete or a consolidate row must be in the baseline with state passed. Failed, error, flaky, skipped or absent is a problem.
  • A delete row needs a kind and the seven evidence fields with text. A consolidate row needs the same and a keeper or a renamed_to. A delete row of kind duplicate or covered needs a keeper. A delete row of kind dead-target needs dead_code in the form of the decisions table.
  • A proof is needed for kind covered (subject failed, keeper failed), kind shape (subject passed), kind test (subject passed), and each speed and fix row (subject failed and after failed). A proof whose row_digest is not the digest of the row now is a problem. The patch must be in proofs/ beside the ledger with the recorded SHA-256.
  • A delete or a consolidate row with a protected value is a problem.
  • A tier row needs tier_runner and tier_cadence.
  • An unknown mark or kind, a key that two rows have, and a key that does not match R[0-9]{3,} with re.fullmatch are problems.
  • A value of the ledger that privacy.private_hits finds is a problem (Task 3 owns privacy.py; until then this rule is a test marked to wait for it).

Rules. collect refuses a tree that is not clean, runs the list command, and stores the IDs with the tree and the command SHA in <store>/collections/ (the two-file pattern of the runs). A list command that exits not 0, or a ListingError, stores nothing and exits 1. For Jest and for Go, whose listings do not name each test, ids refuses a collection and needs two recorded runs of the touched files with one command SHA. ids refuses when the tree of --before is not the before of the batch (decisions table), or when the two refs have different command SHAs.

Rules of reconcile. Only rows with status applied and a batch up to N count. Each ID in before and not in after needs such a delete or consolidate row, or is the old ID of a row with renamed_to. Each ID in after and not in before must be a renamed_to. An applied delete row whose ID is in after is a problem. A keeper that is not in after is a problem; when the after side is a run, a keeper that did not pass is a problem. A dead-target row of this batch whose dead_code is still in the after tree (decisions table) is a problem. A planned row of a later batch is not a problem.

Rules of the report. One HTML file with its own small style sheet. It loads nothing from the network. Each value is escaped. Order: the protected rows (proposals for the person), the rows with no proof, then each delete, consolidate, speed and fix row with its evidence, its keeper and its proof; then the lines of loss (removed tests, fewer_assertions, skips_added); then the numbers. No failure text. The times of two runs are compared only when the machine (label and identity) and the command SHA are equal. The numbers are the processor seconds, the sum of the test seconds, the wall time with the load, and the control of the decisions table. When there is no coverage block, the first section says "coverage not run". report refuses, with exit 1 and the field name, a value that private_hits finds.
