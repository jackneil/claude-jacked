Goal

Ship the skill /test-diet for Claude Code and Codex, and the five commands that it uses: jacked tests ledger verify, jacked tests collect, jacked tests ids, jacked tests covdiff and jacked tests report. A run of the skill makes a repository's test suite smaller and faster on a branch. Each cut has its evidence in a ledger. The run ends with a report and a pull request that a person reviews.

Spec: 2026-11-25-test-diet-design.html, Part 2, "What a run does", "What proves a cut", "Safety rules", "Changes after the plan review", "Changes during the build" and "The owner's answers (2026-11-26)". Recorder: 2026-11-26-test-diet-recorder.html.

What this plan is based on

  • The approved spec: the ledger with its marks and kinds, ledger (it refuses a delete row with a missing field) and ids (the IDs before and after a batch against the ledger).
  • The owner's own prune of 2026-11-24 in one of their repositories: evidence for each cut from a read-only agent, a second agent that argues against each cut, a coverage comparison, and a green gate at the end.
  • The owner's answer of 2026-11-26 on the commands that the review added: build collect, covdiff and report; do not build prove, ledger protect or ledger approve as commands. The planted-defect check stays in the skill text as a method. A second agent runs a sample of those checks again. A run never cuts a protected test; the pull request proposes it.
  • The second review of the older skill plan. Its findings that apply to these commands are in the tasks: the baseline is tied to the tree and the gate command of the ledger; the ledger holds the trees of each batch; the signals of loss are in the skill steps and in the report; the control of the saving has a definition; a dead-target cut and a duplicate cut each have a mechanical check; a proof is tied to the content of its row.
  • The third review of this plan (2026-11-26) and the lead's rulings on it. The decisions and the tasks below answer each of its findings.
  • The recorder code on this branch (jacked/testdiet/), read again at the end of this revision, and the recorder fix list. Where a fix of that list is not in the code yet, the task that needs it names it as a precondition.

What the checks can and cannot do

A model writes the ledger. No local command can stop a ledger that a model forges. Each check in this plan catches a careless error: a missing field, a cut of a test that failed, a proof for a different row or an older body, a removal that no row names, a keeper that does not exist, a tree that is not the tree of the chain, a saving that is noise. The person who reviews the pull request is the last check. The report puts the evidence of each cut in front of that person.

Global constraints

The global constraints of the recorder plan apply. These are added.

  • The skill text is guidance for a model. No point tables, no regular expressions that give a verdict. A name or a text pattern only nominates a test.
  • The new skill has no <!-- ENGINE --> marker and has disable-model-invocation: true and agents/openai.yaml with the exact content of recorder Task 6.
  • A failing test is never a candidate. A red baseline gives a report only.
  • Slow is not a reason to delete. A slow test gets a speed or a tier row.
  • A run never deletes production code (the lead's ruling). See the decision "A dead-target cut".
  • The ledger and the report hold test IDs, numbers and evidence text. No failure message, no log text, no private value of the machine (jacked/testdiet/privacy.py, made in Task 1).
  • Where the commands live. Each new command is in jacked/testdiet/commands.py. jacked/cli.py does not change, because its ratchet entry is exact. Each command body is thin: it reads its options, calls one function of its module, and exits with the code of that function. The checks, the output lines and the exit codes are in the module.
  • Sizes. Each module stays at or under 500 lines, and no ratchet baseline goes up. When a new module passes 400 lines while you write it, split it by responsibility before it gets to 500. Each function has 4 arguments or fewer (JACKED_GUARDRAILS.md); a dataclass holds more.
  • One line for each output line. Each value that a command prints (a test ID, a row key, a path, a stored value) goes through model.one_line, and each line goes out through model.emit. A listing error prints its runner and its line number, never its text.
  • Processes. Never stop a process by a generic pattern (pkill -f, killall). Stop only the processes that you started, by PID. Each brief that can run tests, a layout gate or a server carries this rule.
  • The gate cadence. Each task runs its targeted tests only. The full suite runs one time, at the end (Task 5.4), wrapped by jacked tests run --kind full. /dcr runs beside that gate.
  • The targeted set of a task is its own test files, tests/unit/test_tests_reference.py, tests/unit/test_module_size_ratchet.py, each file that grep -rl <module stem> tests/unit prints for each module that the task changes, and the doctests of those modules.
  • Documents with each command. The task that adds a command adds it to the set that tests/unit/test_tests_reference.py pins, and documents it in the section "Gate recorder (jacked tests)" of jacked/data/rules/jacked-reference.md and of README.md, with its real options, in ASD-STE100 and with no em-dash.

Review focus

  1. A ledger row whose claim is false or stale: a cut of a test that failed in the baseline, a baseline of a different tree or command or a red newer run, a keeper that is skipped in the baseline, a proof that belongs to an older form of the row or an older body of a file, a "covered" cut whose keeper is gone after the batch. Expected: ledger verify or ids refuses each one. Tests in Tasks 1 and 2.
  2. A batch removes a test that no row names, or a consolidation renames tests. Expected: the first fails, the second passes with the map. Tests in Task 2.
  3. A shared fixture change makes every test faster. Expected: the report does not claim a saving against a control that the change touched. Test in Task 3.
  4. The skill starts inside an autonomous run, or on a tree with changes that are not committed. Expected: it stops. The live proof tries both (Task 5).
  5. A test that a rule file protects. Expected: no run cuts it. Its row has the status proposed, and the pull request lists it as a proposal. Tests in Tasks 1 and 2, skill text and live proof.
  6. The ledger is written and committed between two collections. Expected: the chain passes, because trees are compared modulo the run folder. A change outside that folder fails. Tests in Tasks 1, 2 and 3.
  7. A batch deletes a file that holds no test. Expected: ids refuses it. Test in Task 2.

The chain modulo the run folder (CRITICAL 1)The run folder is the folder of ledger.json, relative to the top of the work tree. (7) Commit the ledger. The after_ref of batch N is the before_ref of batch N+1. SKILL.md and ledger.md give this order.collect refuses a tree with changes that are not committed, so each write of the ledger gets a commit before the next collect.
Batches (MEDIUM 3)The ledger holds batches: {"1": {"before": TREE, "after": TREE, "before_ref": ID, "after_ref": ID}, ...}. ids writes the entry of a batch only when its check passes, and only for the next number. ledger verify refuses an applied delete, consolidate, speed, fix or tier row whose batch has no entry, a gap in the batch numbers, and a link of the chain that does not match.Each applied cut is tied to an ID check that passed.

Dead targets and production code

SubjectDecisionReason
A dead-target cut (MEDIUMs 6 and 7)

The spec, "What proves a cut", Dead target: "The test exercises code that does not exist: a removed import, a deleted subject file, a test that is skipped for good." Its proof: "The runner or the dead-code tool shows it. A check that the skip does not hide a real defect."

So the code is already gone in base_tree. A dead-target cut deletes the test only. The field dead_target has one of three forms. "The subject test's own file" is the file of the row's test in the baseline record.

  • path: a file that does not exist in base_tree. The link: the stem of the file (its name with no folder and no extension) is a whole word in the subject test's own file, in the before tree of the batch.
  • path::name: a name that no file of base_tree holds as a whole word, outside the files of the tests of the dead-target rows. The link: the name is a whole word in the subject test's own file, in the before tree.
  • skip: the test is skipped in the baseline and in each recorded run of the store that holds its ID (history.iter_runs and history.load_tests). The row has the unskip proof with subject failed. When the unskipped test fails on an assertion of live code, the skip can hide a real defect: the row is a fix row, not a cut.

Each path passes ids.relative_path. The checks read tree objects through tree.git (git grep -w -F and git cat-file -e on the tree), never the files of the work tree. A common name gives a refusal; that is the safe direction.

A typo, or a name that moved to a different file, fails the link or the absence check. The skipped-test conflict of the older plan goes away: the spec names "a test that is skipped for good" as a dead target, so a dead-target row accepts the baseline state skipped, and only with these checks.
The field dead_codeOne of the seven evidence fields: the spec's "the code that the cut makes dead". It is text, and it is a different field from dead_target. A batch removes such code only when it is test code in a file that holds a test (a fixture or a helper that only the cut tests use). The report lists each dead_code for the person.The two fields had one name in the older plan.
No production code is deleted builder's callids refuses a batch that deletes a file outside the run folder that holds no test. The files that hold a test are the file of each test of the baseline record (the recorder gives it for each runner, and it is the only source for nextest), the file of each test of a run ref, and the file part of each collected ID. A dead helper file stays, and the report lists it. A speed repair can change production code for its measured cause; the spec names "an injected clock" and "a call in the same process and not a subprocess". The report lists each changed file that holds no test, with its batch.The lead's ruling: the plan never deletes production code; this check is the builder's mechanism for that ruling. The spec allows speed repairs to change code. It has no rule that deletes code.

Rules of verify_ledger.

  • Baseline. A ledger with a delete, consolidate, speed or fix row, of any status, needs the baseline of the decisions. If the baseline fails a condition, one line gives the reason, and each such row is a problem.
  • States. The test of a delete or a consolidate row is in the baseline with state passed; a dead-target row also accepts skipped, with the checks of its form. Each keeper is in the baseline with state passed.
  • Evidence. A delete row needs a kind and the seven evidence fields, each with text that is not only white space. A consolidate row needs the same and a keeper or a renamed_to that is not empty. A row of kind duplicate or covered needs a keeper. A row of kind dead-target needs dead_target in one of its three forms.

Rules of ids. --batch is the next batch number. A run ref must pass ran_clean, and its tree must be clean. Open questions

  • The live proof in the owner's Python data service (spec acceptance item) needs the gate machine: a self-hosted runner on a rented Linux machine. It is a separate plan. This plan ships without that proof, and its pull request says so and links the issue.
  • "In the same checkout" (the builder's reading; the owner can correct it). The spec runs a failing set that returns "on the base branch in the same checkout", and its Preflight says that the run "never changes the branch of a checkout that other sessions use". This plan reads "the same checkout" as the run's own worktree of the same clone and machine. A worktree has none of the ignored files of the owner's checkout, so the verdict "the state of the checkout" comes from a pass in the run's worktree beside the red records of the history.
  • The builder's proposal: production code that only tests call. Not in this plan, and not a rule. A later version of the skill could list production code whose only callers are the tests that a run cuts, with its callers, as a candidate for the person. The owner decides if a run may ever delete such code, in its own batch, with a named approval in the pull request. The spec protects "the only test of a public call", so a public call is never such a candidate.
