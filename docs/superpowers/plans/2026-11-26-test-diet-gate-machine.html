Goal

jacked tests run --on <label> -- <gate command> runs a gate on a machine that the user chooses and reaches with ssh (a LAN host, a host on a Tailscale network, a rented server), and records it in the local history. The gate runs the commit that was sent. A lost connection never gives a verdict. The laptop does no test work.

Spec: 2026-11-25-test-diet-design.html: the section "A gate on a different machine", the acceptance item "Gate machine", the table "The owner's answers (2026-11-26)" (the rows "The gate machine" and "A gate on a different machine when the connection drops"), and the table "Changes during the build". The owner asked for two lanes: a runner lane for CI, whose provider is open, and run --on, a gate "on a machine of your own choosing across like ssh via tailscale or something like that" for each user of jacked.

Why this design is smaller than the first one

The second review found nine open defects in the first design. Most of them were in the parts that made it a job runner: a queue, a lock for one full gate at a time, detach and attach, cancel, a run that two sessions share, and pending runs. This design has none of those parts. Two decisions remove them, and the two have different sources:

  • A dropped connection stops the gate, with no reattach. This is the owner's decision. The spec, table "The owner's answers (2026-11-26)", row "A gate on a different machine when the connection drops": "Stop on drop, no reattach". The gate is not detached, no command attaches to it again, and a lost connection gives exit 75 and no record.
  • No lock between gates. This is my call, and the spec section "A gate on a different machine" says so. Two sessions can gate on one machine at the same time. Each record holds the load of the gate machine at the start and the end, so a slow run under load is visible. The machine list gives a worker count, a priority and a free-memory floor for each machine.

These rules follow from the two decisions:

  • A run is attached. One SSH session carries the whole gate. The local command stays in the foreground for the full gate. A session that needs more than the limit of one tool call runs it as a background shell command, in the form cmd > log 2>&1; rc=$?.
  • The driver finds a lost connection in two ways. The first is the end of its standard input. The second is a heartbeat: after the bundle, the local side writes one byte each 15 seconds, and 60 seconds with no byte is a lost connection. The heartbeat is necessary because a laptop that sleeps, or a network path that changes, sends no end of input: the remote SSH server sends no probes by default, and TCP keepalive finds the dead link only after about two hours. The heartbeat is not a part of a job runner. It only tells the driver that its client is alive.
  • The kernel says if a run is alive. A running gate holds an operating system file lock on its run folder. The lock goes away when the last process of the gate ends, for each reason. No PID is probed.

Global constraints

The global constraints of the recorder plan apply. These are added.

  • The driver imports nothing from jacked. It is the package jacked/testdiet/gate_driver/. Each import in it is a module of the standard library or a relative import of the package (from . import grammar). So the same files run as jacked.testdiet.gate_driver in the tests and as the top-level package gate_driver in the archive. It needs Python 3.11 or later, its standard library, and git.
  • The Python floor is jacked's own floor. The driver constant FLOOR = (3, 11) is the lower bound of requires-python in pyproject.toml, and a test compares the two. Hosted CI runs Python 3.11 on Linux, macOS and Windows, so each driver test also proves the floor on the three systems. The driver never uses a call that is newer than the floor without a version branch (for example shutil.rmtree(onexc=...) is 3.12; the copy of the remove rule keeps the onerror branch for 3.11).
  • The driver goes to a gate machine as one archive. jacked/testdiet/driver_build.py builds a zipapp, gate_driver-<HASH12>.pyz, in memory from the package files. Each entry has a sorted place, the date 1980-01-01 00:00:00, the mode 0644 and no compression (ZIP_STORED). There is no __pycache__. So one jacked build always gives the same bytes and the same hash. zipapp.create_archive is not used, because it keeps the file times. HASH12 is the first 12 hex characters of the SHA-256 of the archive. The archive's __main__.py is a copy of gate_driver/archive_main.py. It holds only the floor check and the call of gate_driver.cli.main, in a syntax that each Python 3 can parse. So an older interpreter gets the one refusal line, not a SyntaxError.
  • One grammar for each value that crosses SSH on a command line or becomes a part of a path, checked with re.fullmatch on both sides:
    • RUN: the pattern string of history.RUN_ID_RE, (\d{8})T\d{12}Z-[0-9a-f]{8}. The driver compiles it with re.ASCII, so \d is only 0 to 9. A test asserts that the two pattern strings are equal, and that the driver refuses a RUN with a digit that is not ASCII. RUN is the record's run ID: run --on makes it with history.new_run_id() before the gate, and the run folder, the temporary ref and the record use it. (A local run makes its ID after the gate; a remote run makes it first, because the ID crosses SSH.)
    • SHA: [0-9a-f]{40}([0-9a-f]{24})?. REPO: [0-9a-f]{16}. HASH12: [0-9a-f]{12}.
    • TEMP, the install name: gate_driver-[0-9a-f]{12}\. + RUN + \.part.
    • A verb: one of probe, have, gate, gc, install. The driver also has the verb leader (Windows only). Only the driver starts it, on its own machine; the local side never sends it.
    No other value goes on a remote command line. Each other value (the gate command, the setup command, the environment, the folder, the JUnit globs, the options of gc) goes in a JSON line on standard input.
  • REPO is the first 16 hex characters of the SHA-256 of the sorted root commits of the repository, joined by a newline. A repository can have more than one root commit.
  • Process control. On POSIX, the driver signals only the process group that it made, and only while the group leader is not reaped. On Windows, the driver stops only the job object that it made, and it calls no os.kill. The decision "The life of a gate" gives the mechanisms.
  • A delete is self-evidencing. The driver and gc delete a run folder only when the rule of the decision "Live runs and gc" holds. The rule reads only the folder's own name and content.
  • The gate machine is less trusted than the local machine. Each value of the result is checked for its type and its bound. Each stream is written under a name that the local side makes, in a new private folder, and checked with its SHA-256. The recorder's JUnit reader reads it. The gate output goes through the output filter of the decision "Reading the result".
  • jacked's own messages never hold the SSH destination, the remote root, a remote absolute path or a machine identity. This applies to the local side and to the driver. A message names the label. The own errors of ssh go to a private log (-E), and a message gives the exit code and the local path of that log. The driver prints paths relative to its root (runs/<RUN>/...). It captures the standard error of git and prints one line with the exit code of git. Its main() catches an unexpected exception and prints its class name only; the traceback goes to root/driver.log. The gate's own output is the output of the user's own command: it passes through the output filter and can hold remote paths (pytest prints rootdir:).
  • No test opens a network connection or starts ssh or scp. An autouse tripwire in tests/conftest.py enforces it (Task 1). The tests use LocalTransport: the built archive as a child process, with a temporary home and a pipe pair. The live proof covers the real SSH paths (Task 5).

Review focus

  1. The connection drops or the local command is stopped during the gate. Expected: exit 75 and no record on the local side. On the gate machine, the gate and its child processes stop at once at the end of input, and at most 71 seconds after the last heartbeat byte when the link goes silent (60 s of silence, 1 s for the check, 10 s of grace). The folder is removed or gc can remove it. Tests in Tasks 2 and 3; live proof in Task 5.
  2. A value that changes the meaning of a command or a path: a RUN of .., a have answer of --all, an ssh value that starts with - or holds @, a header with a JUnit glob or a folder of ../x, an argument with & or %PATH%. Expected: refused on both sides, or passed as typed with no shell. Tests in Tasks 1, 2 and 3.
  3. A wrong or hostile answer from the gate machine: a size that is not an integer, a result line of 2 MiB, a stream with a wrong SHA-256, a result with a commit that was not sent, a different machine identity, a JUnit file with a DOCTYPE, an OSC 52 escape in the gate output. Expected: no verdict, nothing written outside the private folder, no escape on the terminal. Tests in Task 3.
  4. Two sessions gate on one machine at the same time, and one runs gc. Expected: gc never removes the folder of a live gate. Tests in Task 2.
  5. The driver dies while the gate lives (the OOM killer near the floor, a kill -9). Expected: gc keeps the folder until the last process of the gate is gone. Test in Task 2.
  6. A tree with changes that are not committed. Expected: --on refuses it, because only a commit can be sent. Test in Task 3.

The default priority is low; there is no default floor. The grammar, checked at each load and each write: a label matches LABEL_RE and is not local (the label of local records); ssh matches [A-Za-z0-9][A-Za-z0-9._-]* (a Host alias of the SSH configuration or a MagicDNS name, with no @, : or /); python matches [A-Za-z0-9_][A-Za-z0-9._/\\:-]* (so ., .. and -c are refused); workers and min_free_mb are integers of 1 or more. Each one gives a protocol error and exit 75, never a verdict. machines add tells the user to connect one time by hand to accept the host key. A host key failure gives exit 75 and the log path. The gate machine never gets the local SSH agent. What crosses is the full history that the commit reaches and the --env values, so the host key must be known (the first value of an option wins, and the command line comes first). No run becomes a channel of a master connection that a different ssh opened, with keepalive settings of its own. PermitLocalCommand=no stops a LocalCommand of the user configuration from writing into the result stream. The local ssh finds a dead link in about one minute; the gate machine finds it with the heartbeat.
Driver installscp sends the archive to TEMP in the remote home. <python> <TEMP> install checks that the first 12 hex characters of the SHA-256 of its own file are the hash in its name. It makes or checks the root, then moves itself with os.replace to .jacked-gate/drivers/gate_driver-<HASH12>.pyz. probe answers with the hash of the driver that runs. When Python cannot open the driver file (Python's own exit code 2), run --on installs the driver and probes one more time. Old drivers stay; gc lists them, and removes each one other than the running one only when its options ask for it and no run folder is live.Two jacked builds must not replace each other's driver in the middle of a run. A driver file is about 100 KB, so to keep old ones costs nothing that matters.
Driver exit codes0: done. 64: a refused value. 65: a protocol error (the header, the bundle, a byte after the bundle that is not the heartbeat byte). 66: Python is older than the floor; one line names the two versions. 75: stopped, no verdict. Never 2, which is Python's own code for a file that it cannot open. The exit code of the gate travels in the result line, never as the exit code of the driver or of ssh.The local side must tell "no driver" from "a refused value", and the exit 255 of ssh from a gate code.
Root on the gate machine~/.jacked-gate, resolved by the driver with Path.home() (HOME on POSIX, USERPROFILE on Windows). No path crosses SSH. The root, drivers, repos and runs have mode 0700 on POSIX. The driver refuses a root that is a link, that the user does not own, or that group or others can write. root/driver.log (mode 0600) holds the traceback of an unexpected error and the messages of a stop that it cannot print. The machine identityThe driver keeps 32 random hex characters in root/machine-id. probe and the result of gate give it. machines add stores it in the list. Each run --on probes before the bundle, and the probe and the result must give the stored identity. A mismatch gives exit 75, no record, and one line that names the label and the command that accepts a planned change: jacked tests machines probe LABEL --accept (or remove and add). seen --on LABEL uses the stored value and opens no connection. Sending the commithave REPO gives the tips of refs/jacked/keep/* of the gate clone, one SHA on each line, and nothing else. The local side checks each element: the SHA grammar first; then one git cat-file --batch-check with the elements on standard input keeps the commits of the local repository; then git merge-base --is-ancestor --end-of-options <tip> <sent> for each one that is left. An element that fails a check is dropped with one printed line. The local side makes a temporary ref refs/jacked/gate/<RUN>, makes a bundle of that ref with git bundle create ... --stdin (the ref and each kept tip as ^<sha> on standard input), and deletes the ref.A bundle needs a ref name. The tips are few, because the driver keeps only the keep refs that no other keep ref contains.
The headerThe first line of standard input of gate is one JSON object: command (the argv list), setup (a string, or null), env (key to value), junit (globs relative to the worktree folder), folder (the gate folder relative to the top of the work tree, "." at the top), workers, priority, min_free_mb (or null), bundle_size (bytes), silence_seconds. Then the bundle bytes. Then one heartbeat byte, ., each 15 seconds, until the result ends. The driver refuses a line longer than 1 MiB; a glob or a folder that is absolute, that holds a .. part or a backslash; an env key that does not match [A-Za-z_][A-Za-z0-9_]* or that starts with JACKED_GATE; a silence_seconds that is not an integer from 5 to 60 (run --on always sends 60). The driver never writes the header to a file.A value on standard input needs no quoting and is not visible in a process list. The folder is a part of the run identity (the spec table "Changes during the build", row "The folder of the gate"). A child-process test of the heartbeat sends 5, so the driver needs no test-only variable, and no client can make the limit longer than 60.
The gate clone and the worktreerepos/<REPO>.git, bare, with core.autocrlf=false, core.fsmonitor=false, core.logAllRefUpdates=false and core.hooksPath at the null device. Each git call of the driver has -c gc.auto=0 -c maintenance.auto=false and the environment GIT_TERMINAL_PROMPT=0. The bundle goes into refs/jacked/gate/<RUN>. The worktree is runs/<RUN>/tree, made with git worktree add --detach. The driver checks that its HEAD is the sent SHA. Then git update-ref moves the ref to refs/jacked/keep/<SHA> (one ref for each sent commit), and the driver deletes each keep ref that git for-each-ref --merged=<SHA> refs/jacked/keep/ lists, other than the new one. The gate runs in runs/<RUN>/tree/<folder>.Nothing of a repository runs on a fetch or a worktree add. No git process of the driver outlives it as a detached automatic gc. The keep refs are a cache: a deleted one costs one larger bundle, and no data. A keep ref that a newer one contains adds nothing.
The gate commandThe gate runs as argv with no shell, on POSIX and on Windows, as run_gate does. Each {junit} in each element becomes the absolute path of runs/<RUN>/reports/junit.xml (the rule of reports.placeholder). On Windows, a bare program name is found with a search of PATH only, with PATHEXT and never in the current folder: a copy of the rule of jacked.findbin.find_on_path, as process._program uses it. Only --setup, a string by nature, uses a shell: /bin/sh -c <text> on POSIX, and on Windows the string form of Popen with <cmd> /d /s /c "<text>", where <cmd> is the absolute path from GetSystemDirectoryW, the rule of jacked.winproc.system_program. The driver finds git one time, with the same PATH-only search, before it changes to a worktree. The setup and the gate run in the gate folder, with the null device as standard input, and with JACKED_GATE=1 and JACKED_GATE_WORKERS. No local variable goes to the gate machine unless --env KEY names it; no value is printed or recorded. $JACKED_GATE_WORKERS is not expanded in argv; a script of the repository reads it. A setup that fails gives no gate, and the result says setup-failed with the exit code of the setup.The same typed argv means the same thing on the two machines, as command_sha says. No argv quoting is complete for cmd.exe (it expands %VAR% inside quotes), so the gate never goes through it. A new worktree has none of the files that git ignores; the setup provides them. The driver cannot import jacked.findbin or jacked.winproc, and the scanners of jacked/ parse its files too.
Priority and the free-memory floorPriority low: on POSIX, the argv starts with nice -n 10; on Linux, when ionice is on PATH, with ionice -c 2 -n 7 nice -n 10 (the best-effort class at its lowest level). On Windows, the leader starts with BELOW_NORMAL_PRIORITY_CLASS, and each child inherits it. The floor: the driver reads the free memory before the setup, and each 5 seconds during the setup and the gate. The source for each OS: Linux, MemAvailable of /proc/meminfo; Windows, GlobalMemoryStatusEx().ullAvailPhys with ctypes. macOS: my call: no floor. machines add and set refuse a floor for a macOS machine with one line, and the probe prints "free memory: not available". Below the floor at the start, there is no gate. Below it during the run, the driver takes the stop path of "The life of a gate". In both cases it prints one line with the two numbers, and the result says memory-floor.The owner's answer of 2026-11-26: their Windows machine is a gate machine "at low priority", and it also runs other work. nice and BELOW_NORMAL lower only the processor priority, so the floor is the only memory protection, and a gate can take memory after its start. On Linux, MemFree is near 0 on a busy machine because of the page cache; MemAvailable is the right value. macOS has no value in the standard library and no single documented "available memory" value of the same kind; a guessed value would stop gates at random. The idle class of ionice can starve a gate on a busy disk. A floor that the user sets is not an arbitrary cap.
The life of a gateThree threads. The input thread reads standard input after the bundle, one byte at a time; each beat sets the time of the last beat. The watch thread wakes each second. The main thread starts the setup, waits for it, then starts the gate and waits for it. The setup and the gate each start as a leader of their own, and each gets the same stop path. These are the stop conditions: the end of input; a byte that is not the beat; silence_seconds with no beat; free memory below the floor; and the exit of the leader by itself (then the stop path stops the leftovers).
POSIX. The leader starts with start_new_session=True, so the group ID is the PID of the leader. The main thread finds the exit of the leader with no reap: on Linux, os.waitid(os.P_PID, pid, os.WEXITED | os.WNOWAIT); on macOS, select.kqueue with KQ_FILTER_PROC and KQ_NOTE_EXIT (CPython 3.11 and 3.12 for macOS have no os.waitid, checked on 2026-11-26). The zombie keeps its PID, so the group ID stays reserved. The stop: SIGTERM to the group; a wait of at most 10 seconds, which ends early when the group has no live member other than the leader (Linux: the group field and the state of /proc/<pid>/stat; macOS: /bin/ps -A -o pid= -o pgid= -o stat=); SIGKILL to the group; then the reap with Popen.wait(), which gives the exit status that the zombie holds. One lock guards the flag reaped. The watch thread signals only under that lock, and only while reaped is False. The main thread sets reaped under that lock before it reaps. A member that calls setsid() leaves the group, and the driver cannot stop it; the reference says so.
Windows. The driver makes a job object (CreateJobObjectW, JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, no breakaway flag; a nested job needs Windows 8 or later). For the setup, and then for the gate, it starts <python> <archive> leader with a pipe as its standard input, assigns that leader to the job, and only then writes one JSON line to it: the argv (or the setup text), the folder and the environment. The leader starts the command, with the null device as its standard input, waits for it, and exits with its code. Popen gives no handle to resume a process that it started suspended, so the leader is the way that nothing of the gate starts outside the job. The stop is TerminateJobObject, with no grace time: the driver has no signal for a console process without os.kill. After the leader exits by itself, TerminateJobObject also stops the leftovers. A job handle is not a PID, so it cannot reach a process of other work.
The silence path writes nothing to standard output or standard error. On a half-open channel, each write blocks, as the gate does. So the stop decision, the stop and the delete never wait on a write, and their messages go to root/driver.log. The watch thread also runs while the result is written: when silence_seconds pass with no beat in that phase, it ends the driver with os._exit(75). Nothing is left on the disk at that point.
The time line after the last beat: at most silence_seconds (60), plus 1 second for the check, plus 10 seconds of grace (POSIX). So no process of the gate is left after 71 seconds. At the end of input the stop starts at once.		A laptop lid or a network change gives no end of input. During the silence, the gate fills the SSH channel window and blocks on its own output, so it would hold the folder, the worktree, a test database copy and its memory for about two hours. A killpg after the reap can reach an unrelated group that got the same ID. A gate that exits by itself can leave a database server, an xdist worker or a background job in its group. On Windows, the job of the SSH session stops the session processes only when the session ends, and it allows breakaway.
Live runs and gcgate makes runs/<RUN>, then takes an exclusive lock on runs/<RUN>/active.lock, then writes the marker run.json ({"run": "<RUN>"}), and only then writes anything else.
POSIX: fcntl.flock. The descriptor goes to the setup and the gate with pass_fds. A flock belongs to the open file description, so the lock is free only when the last process of the gate is gone, also when the driver dies. Before the delete, the driver closes its descriptor, opens a new one, and takes the lock with no wait. When it cannot, a process of the gate still lives: the folder stays for gc, and one line in the driver log says so. A process that closes its inherited descriptors (Python's subprocess does that by default) does not hold the lock, but the leader that started it does, as long as it lives. A process that also leaves the group (a daemon) escapes the lock and the stop. The gate is over at that point, so no verdict changes, and gc can delete the folder under that process. The reference says so.
Windows: msvcrt.locking on byte 0. The handle is not inherited. The job gives the same guarantee: the death of the driver closes the job handle, and KILL_ON_JOB_CLOSE stops the gate. Windows does not delete an open file, so the driver releases and closes the lock before it deletes active.lock.
The delete order, on each OS: (1) git worktree remove --force of the tree, then the remove rule for what stays (a copy of the rule of cleanup.remove_tree_quietly: a read-only file gets write permission and the delete tries again); (2) each other entry, other than the marker and active.lock; (3) release the lock, close it, delete active.lock; (4) the marker; (5) the empty folder, with rmdir, never rmtree. A delete that stops part way keeps the marker, so gc can finish it.
The rule of gc: it removes a run folder only when its name is a RUN; it is inside root/runs after the path is resolved; it is not a link; it holds a marker that names its own RUN; and either it can take the lock with no wait, or active.lock is missing and the marker is the only entry. gc also runs git worktree prune for each clone. Its options come in one JSON line on standard input: keep_ref_days (or null) deletes each keep ref whose commit has a committer date older than that number of days, then runs git gc --prune=now; old_drivers (true or false). It prints each folder, keep ref and driver that it removes and each that it keeps.		The system releases a lock when a process ends, for each reason. A PID can be used again. The OOM killer near the floor kills the driver, not the gate, and gc must then not delete a worktree under a live gate. The age of a keep ref is the committer date of its commit, my call: it needs no state of its own, and a wrong delete costs one larger bundle.
The resultThe order: the gate ends; the stop path stops the leftovers; the reap; the status of the worktree; the reports are read into memory; the run folder is removed by the delete order; then the result is written. The result is one JSON line on standard output: schema (1), exit_code, wall_seconds (the gate only), setup_seconds (or null), child_cpu_seconds (or null), load_start, load_end (or null), free_mb_start (or null), commit, clean_after, report_root, machine_id, streams (a list of {"kind": "junit" | "changed", "size": N, "sha256": "<64 hex>"}). Then the bytes of each stream, in order. A stop that can still write gives {"schema": 1, "stopped": "setup-failed" | "memory-floor" | "protocol", ...} with its numbers. clean_after is True when git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=none in the worktree prints nothing (ignored files are not in it). The status compares with the sent commit, so a change by the setup counts. The changed stream holds the paths of that status, relative to the repository, separated by NUL. child_cpu_seconds is the processor time of the gate only: on POSIX, the difference of RUSAGE_CHILDREN before and after the gate (the setup and git are outside it); on Windows, the difference of the user and kernel time of the job (JobObjectBasicAccountingInformation) before and after the gate. The gate's own output goes to standard error, live.One session, no second fetch step, no window in which a finished run waits for a client. The run folder is gone before the write, so a write that never ends leaves nothing on the disk. A setup that rewrites a tracked lockfile (npm install and package-lock.json, uv sync and uv.lock) makes each remote run "tree changed"; the reference says so. The paths go as a stream, so the result line holds only small values and its limit is real.
Reading the resultThe local side reads the result line with a limit of 1 MiB; a longer line is refused, logged and gives exit 75. Each value is checked for its type: an exit code is an integer from 0 to 255 and not a boolean, a size is a non-negative integer, a SHA-256 is 64 hex characters, the commit is the sent SHA, the machine identity is the stored one, report_root is an absolute path of at most 4096 characters with no NUL. The local side uses report_root only to make the paths of the report relative; it never prints or records it. Each stream goes to a file of a new private folder (mode 0700), under a name that the local side makes (junit-<n>.xml, changed), with its SHA-256 computed while it is written. A size larger than the free space of the disk of that folder (shutil.disk_usage) is refused with one line that gives the two numbers; that is a real limit, and the refusal is logged. A wrong value, a wrong SHA-256, a short read, or an ssh exit of 255 gives exit 75 and no record. Then read_junit(..., root=<top>, report_root=<report_root>) reads the reports, the changed paths print as in a local run (one emit line each), and the folder is removed.
The output filter, my call: the local side copies the gate output from the standard error of ssh to its own standard error through a filter. The filter decodes UTF-8 with an incremental decoder (errors="replace"). It keeps text, newline, carriage return, tab and SGR color sequences (ESC [ digits and ;, then m). It removes each other control character (C0, DEL, C1) and each other escape sequence (OSC, which holds the clipboard write OSC 52; DCS; any other CSI). A sequence that two reads split is handled. The lines of the driver pass through the same filter.		A wrong type is not a verdict. A wrong or hostile machine must not fill the memory or the disk of the laptop, or write to its clipboard. A local gate's output passes raw, because the local machine is the user's own. The SHA-256 of each stream also proves that Windows OpenSSH did not change a byte.
