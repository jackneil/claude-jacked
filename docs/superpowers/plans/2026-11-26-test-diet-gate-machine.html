Goal

jacked tests run --on <label> -- <gate command> runs a gate on a machine that the user chooses and reaches with ssh (a LAN host, a host on a Tailscale network, a rented server), and records it in the local history. The gate runs the commit that was sent. A lost connection never gives a verdict. The laptop does no test work.

Spec: 2026-11-25-test-diet-design.html, section "A gate on a different machine", acceptance item "Gate machine", and the owner's answers of 2026-11-26. The owner asked on 2026-11-26 for both lanes: a self-hosted runner on a rented box for his private repositories, and a gate "on a machine of your own choosing across ssh via tailscale or something like that" for each user of jacked.

Why this design is smaller than the first one

The second review found nine open defects in the first design. Most of them were in the parts that made it a job runner: a queue, a lock for one full gate at a time, detach and attach, cancel, a heartbeat, a run that two sessions share, and pending runs. These are my calls, and they remove each of those parts:

  • A run is attached. One SSH session carries the whole gate. The local command stays in the foreground for the full gate. A session that needs more than the limit of one tool call runs it as a background shell command, in the form cmd > log 2>&1; rc=$?.
  • The connection is the life of the gate. When the driver reads the end of its standard input, it stops the gate and exits with no verdict. A connection that drops with no end of input lets the gate run to its own end, and the driver then exits. No gate waits for a client that is gone.
  • No lock between gates. Two sessions can gate on one machine at the same time. Each record holds the load of the gate machine at the start and the end, so a slow run under load is visible. The machine list gives a worker count for each machine.
  • The kernel says if a run is alive. A running gate holds an operating system file lock on its run folder. The lock goes away when the process ends, for each reason. No PID is probed.

Global constraints

The global constraints of the recorder plan apply. These are added.

  • The driver imports nothing from jacked and needs only Python 3.8 or later, its standard library, and git.
  • One grammar for each value that crosses SSH on a command line or becomes a part of a path, checked with re.fullmatch on both sides. RUN: [0-9]{8}T[0-9]{6}Z-[0-9a-f]{8}. SHA: [0-9a-f]{40}([0-9a-f]{24})?. REPO: [0-9a-f]{16}. A verb: one of probe, have, gate, gc, install. No other value goes on a remote command line. Each other value (the gate command, the setup command, the environment, the JUnit globs) goes in the JSON header on standard input.
  • REPO is the first 16 hex characters of the SHA-256 of the sorted root commits of the repository, joined by a newline. A repository can have more than one root commit.
  • The driver signals only the process group that it made, and only before it waits for its leader. A child that the parent has not waited for keeps its PID. On Windows the driver calls no os.kill.
  • A delete is self-evidencing. The driver deletes a folder only when it is inside root/runs after the path is resolved, is not a link, holds the marker file that the driver wrote, and its run lock can be taken.
  • The gate machine is less trusted than the local machine. Each value of the result JSON is checked for its type. A file from it is written under a name that the local side makes, in a new private folder, and read by the recorder's JUnit reader.
  • The SSH destination and the remote root are never printed and never recorded. A message names the label. The standard error of ssh itself (not the gate's output) goes to a private log file, and the message gives the exit code and the path of that file.
  • No test opens a network connection. The tests use LocalTransport: the driver as a child process with a temporary root and a pipe pair. The live proof covers the real SSH paths.

Review focus

  1. The connection drops or the local command is stopped during the gate. Expected: exit 75 and no record on the local side; on the gate machine, the gate stops when its input ends, and its folder is removed or can be removed by gc. Tests in Tasks 2 and 3; live proof in Task 5.
  2. A value that changes the meaning of a command or a path: a RUN of .., a have answer of --all, an ssh value that starts with -, a header with a JUnit glob of ../x. Expected: refused on both sides. Tests in Tasks 1 and 3.
  3. A wrong or hostile answer from the gate machine: a size that is not an integer, a file name with a separator, a result with a commit that was not sent, a JUnit file with a DOCTYPE. Expected: no verdict, nothing written outside the private folder. Tests in Task 3.
  4. Two sessions gate on one machine at the same time, and one runs gc. Expected: gc never removes the folder of a live gate. Tests in Task 2.
  5. A tree with changes that are not committed. Expected: --on refuses it, because only a commit can be sent. Test in Task 3.

SubjectDecisionReason
Machine listjacked_home()/.claude/jacked-gate-machines.json, written only by the machines commands through atomic_write_bytes with mode 0600: {"version": 1, "machines": {"<label>": {"ssh": "<alias>", "python": "python3", "workers": N, "machine_id": "<32 hex>"}}}. A load refuses a file that group or others can read (POSIX), an ssh value that starts with - or holds white space, and a python value outside [A-Za-z0-9._/\\:-]+. The documentation tells the user to put an alias of the SSH configuration in ssh, so that the list holds no address.The address stays local. jacked keeps its state in .claude/ under its home.
TransportEach step is ssh -a -x -T -o BatchMode=yes -o ClearAllForwardings=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=4 -- <alias> <python> <driver file> <verb> <values of the grammar>. ssh, scp and git come from jacked.findbin.find_bin. Tried on a Windows host on 2026-11-26: 1 MB of binary standard input arrived with the same SHA-256.A value of the grammar needs no quoting in a POSIX shell or a Windows shell. The gate machine never gets the local SSH agent. A dead connection is found in about one minute.
Driver installThe driver file is gate_driver-<first 12 hex of its SHA-256>.py in the remote home. scp sends it to a temporary name; install checks its own hash and renames itself. probe answers with the hash of the driver that runs.Two jacked builds must not replace each other's driver in the middle of a run.
Root on the gate machine~/.jacked-gate, resolved by the driver. No path crosses SSH. The root, repos and runs have mode 0700 on POSIX. The driver refuses a root that is a link, that the user does not own, or that group or others can write.A Windows shell does not expand ~.
The machine identityThe driver keeps 32 random hex characters in root/machine-id. probe and the result of gate give it. machines add stores it in the list. seen --on LABEL compares with the stored value and opens no connection.The recorder never compares two machines, and seen must not wait on a network.
What is sentOnly a commit. --on refuses a tree with changes that are not committed. The record holds the tree of that commit.A bundle carries commits, not a working tree.
Sending the commitThe local side makes a temporary ref refs/jacked/gate/<RUN>, makes a bundle of that ref without the commits of the have answer, and deletes the ref. Each element of the have answer must match the SHA grammar, be a commit in the local repository, and be an ancestor of the sent commit; if not, it is dropped with one printed line. The elements go to git on standard input, never as arguments.A bundle needs a ref name. A have answer of --all must not widen the bundle.
The headerThe first line of standard input of gate is one JSON object: command, setup (or null), env (key to value), junit (globs relative to the worktree), workers, bundle_size (bytes). Then the bundle bytes. Then the input stays open. The driver refuses a header with a glob that is absolute or holds .., an env key that does not match [A-Za-z_][A-Za-z0-9_]* or starts with JACKED_GATE.A value on standard input needs no quoting and is not visible in a process list.
The gate clone and the worktreerepos/<REPO>.git, bare, with core.autocrlf=false, core.fsmonitor=false and core.hooksPath at the null device, and GIT_TERMINAL_PROMPT=0. The bundle goes into refs/jacked/gate/<RUN>. The worktree is runs/<RUN>/tree, made with git worktree add --detach; the driver checks that its HEAD is the sent SHA.Nothing of a repository runs on a fetch or a worktree add.
The gate commandThe driver runs the setup (when given) and then the gate with /bin/sh -c on POSIX and cmd.exe /d /s /c on Windows, in the worktree, with the null device as standard input. Each {junit} in the command becomes a path in runs/<RUN>/reports/. It sets JACKED_GATE=1 and JACKED_GATE_WORKERS. No local variable goes to the gate machine unless --env KEY names it; no value is printed or recorded. A setup that fails gives no gate and exit 75.A new worktree has none of the files that git ignores. The repository says how to provide them.
The life of a gateA thread of the driver reads standard input after the bundle. At the end of input: on POSIX, the driver sends SIGTERM to the process group of the gate (the gate starts in a new session, so the group ID is the PID of its leader), waits 10 seconds, then sends SIGKILL, all before it waits for the leader; on Windows, the driver exits, and the job of the SSH session stops the processes of the session. Then the driver exits with no result. Tried on a Windows host on 2026-11-26: a process that the SSH session started died when the session ended, unless it broke away from the job.No gate outlives its client for long, and the driver needs no PID check.
Live runs and gcgate takes an exclusive operating system lock on runs/<RUN>/active.lock (fcntl.flock on POSIX, msvcrt.locking on Windows) before it writes anything else into the folder, and holds it until the folder is gone. gc removes a run folder only when the self-evidencing rule holds and it can take that lock with no wait. It prints each folder that it removes and each that it keeps.The system releases the lock when a process ends for each reason. A PID can be used again.
The resultAfter the gate, the driver writes one JSON line on standard output: exit_code, wall_seconds, child_cpu_seconds (or null), load_start, load_end (or null), commit, clean_after, report_root, machine_id, files (a list of {"size": N}). Then the bytes of each file, in order. Then it removes the worktree and the run folder. The gate's own output goes to standard error, live.One session, no second fetch step, no window in which a finished run waits for a client.
Reading the resultEach value is checked for its type: an exit code is an integer from 0 to 255 and not a boolean, a size is a non-negative integer, the commit is the sent SHA, the machine identity matches 32 hex characters. A wrong value, a short read, or an ssh exit of 255 gives exit 75 and no record. Each file is written to a new private folder under a name that the local side makes, then read with read_junit(..., report_root=<report_root>), then the folder is removed.A wrong type is not a verdict.
The recordSource run, the label as machine, the remote machine_id, the tree of the sent commit, tree_changed from clean_after, the remote load and processor time, the command SHA of the typed command. run --on returns the gate's exit code, or 75 when no verdict came back.The same rules as a local record.

The second lane: a runner box for CI

This lane is infrastructure, not jacked code. The owner chose a rented Linux box in his own account for self-hosted GitHub Actions runners, in the pattern that he operates today: one fresh, walled-off container for each job, a single-use runner registration, a time limit. The provider is open: the owner asked on 2026-11-26 about a provider where he already has an account, and about the platform where his services run. A research report compares them; the owner picks.

The same box is the POSIX gate machine of Task 5.1, under a second user, so a gate over SSH and a CI job never share files.

The setup is a separate runbook that the main session writes after the order, and walks before it hands it over. It holds: the operating system and Docker; a supervisor that starts the runner containers; one runner registration for each private repository that uses it; and a test of the copy of a large test database on the box's file system before any real job. Each step that writes to the box is named before it runs.
