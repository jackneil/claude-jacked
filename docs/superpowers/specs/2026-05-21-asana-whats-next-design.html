Goal

Extend the jacked tool's /whats-next skill so that Asana tasks assigned to the user become a first-class input source alongside GitHub issues, TODOs, and planning docs. Tasks that touch the current repository are blended into the same tier-ranked recommendation list — Asana origin is metadata on the Evidence line, not a privilege that bumps priority.

Design constraint: Jacked commands are LLM instruction files, not code. This spec describes natural-language guidance Opus will read and apply at runtime — not Python scoring, regex engines, or algorithmic detection. Bash one-liners only where they genuinely gather data (env probes, MCP availability checks, git/gh queries).

Architecture

Two layers in the existing jacked architecture. No new top-level slash commands.

  • Setup layer — /jacked-setup whats-next grows an Asana detection + discovery phase. It probes for an access method, runs zero-touch discovery, and emits a new ## Asana Integration block inside the standalone ## Repo Config header it already generates.
  • Runtime layer — the embedded engine in ~/.claude/commands/whats-next.md grows a Step 3.5: Pull Asana signals between the existing GitHub-issue step and lifecycle inference. The step reads the config block, fetches the user's open tasks via the configured access method, and feeds qualifying tasks into the existing Step 5 synthesis pool.

Both layers are guarded by the same access-method config: if Asana isn't reachable, the setup wizard writes an install hint and the runtime step is skipped silently. The rest of /whats-next works exactly as it does today.

Access detection

The wizard tries three methods in order and caches the winner in the config. Runtime re-validates the cached choice cheaply and falls through to the next method if the cached one suddenly fails.

MethodProbeUse when
mcp The Asana plugin directory exists at ~/.claude/plugins/marketplaces/*/external_plugins/asana/ AND the mcp__claude_ai_Asana__* tools resolve (any authenticate tool present is sufficient to confirm). Default for Claude Code users. OAuth is handled by the plugin so no token management is needed.
cli command -v asana or command -v asana-cli returns a path; running --version exits 0. User has a community Asana CLI installed. Uncommon but supported.
rest-pat Env var ASANA_PERSONAL_ACCESS_TOKEN (or ASANA_TOKEN) is non-empty, and curl -s -H "Authorization: Bearer $TOKEN" https://app.asana.com/api/1.0/users/me returns HTTP 200. Headless, CI, or users who prefer a personal-access-token workflow.
none All three probes fail. Wizard writes an install hint block; runtime silently skips Step 3.5.
Install hint when access is none: the wizard writes the following into the config block (instead of workspace/project data) so anyone who opens the file later — including teammates who cloned the repo and don't have jacked installed — knows exactly how to enable it. Re-running /jacked-setup whats-next picks up the change. 
## Asana Integration

- **Access**: none
- **To enable**: `/plugin install asana` (recommended) — or set `ASANA_PERSONAL_ACCESS_TOKEN` from
  https://app.asana.com/0/my-apps — or install asana CLI. Then re-run `/jacked-setup whats-next`.

Setup-time wizard

Three additions to the existing /jacked-setup whats-next instruction body (in jacked/data/commands/jacked-setup.md).

Addition 1 — Access probe block in Step 3 (target-specific analysis)

Run the three probes from the table above in order. Stop at the first success. Save the winning method name as the Access field. If all three fail, write the install-hint block and skip the rest of the wizard's Asana phase.

Addition 2 — Zero-touch discovery (only if access succeeded)

Using the chosen access method:

  1. Fetch the current user's GID (users/me) and cache it in the config — runtime never re-queries this.
  2. List the user's workspaces. Show the count to the user.
  3. List the projects the user is a member of in each workspace. Show the count.
  4. Ask one question: "Track tasks across all N workspaces / M projects, or pick specific projects? [all/pick]" — default all. If pick, present the project list and let the user select.

Addition 3 — Priority custom-field sniff

Examine the custom_fields of a sample of selected projects (one or two — Asana custom fields are defined per-project but commonly shared). Look for a field whose name matches Priority, Status, Tier, P0, P1, or similar. If found, save the field's GID and the list of allowed enum values. Do NOT pre-bake a values-to-tier mapping — Opus maps them with judgment at runtime using the existing tier framework.

When the user re-runs /jacked-setup whats-next, the wizard reads the existing block (if any), re-probes access, re-asks the all/pick question with the prior choice as default, and overwrites. Same upgrade flow as every other jacked-setup target.

Runtime behavior (Step 3.5)

A new step is added to the engine in ~/.claude/commands/whats-next.md, placed between current Step 3 (GitHub signals) and Step 4 (lifecycle inference). The instruction body in plain English looks like:

Step 3.5: Pull Asana signals. Skip this step entirely if ## Asana Integration is missing from the config or its Access field is none. Otherwise, using the access method declared in config (MCP / CLI / REST+PAT), fetch open tasks assigned to the configured user GID across the configured workspaces and projects. Pull title, notes (truncated to ~500 chars), due date, project name, section name, the configured priority custom field if any, and the task URL. For each task, judge repo-relevance and importance using the criteria in the next section. Drop tasks with no plausible connection to this repo. Feed the survivors into Step 5's candidate pool with source: "asana" metadata.

This step is constant-time per task — Opus reads the task content and makes a judgment. There is no scoring formula, no points table, no regex matcher. The full set of tasks for a typical engineer is on the order of dozens, well within Opus's working budget per turn.

How Opus judges tasks

Repo relevance

For each task fetched, the engine guidance reads:

Read the task title and notes. Decide whether this task is plausibly about the codebase the user is currently working in. Strong evidence: a github.com/<owner>/<repo> URL pointing at this repo (use git remote get-url origin to know the repo), the repo's basename appearing as a discrete word, or specific file paths and module names from this repo being mentioned. Weaker evidence: the Asana project name resembles the repo name, or the task references features and people clearly tied to this codebase. If the task is plainly about something else — an unrelated product, a personal todo, a recurring meeting — drop it. If it's genuinely ambiguous, keep it but mark low confidence on the Evidence line so the user can disambiguate.

Importance

Slot kept tasks into the same Tier 1-5 framework already used in Step 5 of the engine. The engine guidance reads:

Use the priority custom field value (if configured) as the primary tier hint: P0 / Blocker → Tier 1, P1 / High → Tier 2, P2 → Tier 3, P3 / Low → Tier 4-5. Shift up one tier if the due date is overdue or within three days. Shift down if the task is parked in a section named Backlog, Icebox, Someday, or similar. For tasks with no priority field and no due date, default to Tier 3 and let your reading of the title and notes inform impact and effort.
Asana origin is metadata for the Evidence line — Asana <task-short-id> in <project> — not a tier bonus. A trivial Asana task (e.g. "Move sticky notes to new board") does not outrank a critical bug surfaced from GitHub issues. The user explicitly called this out during brainstorming.

Explicit non-goals (YAGNI)

  • No write-back to Asana — read-only. We do not complete tasks, post comments, or create subtasks from /whats-next.
  • Assigned-to-me only — no follower/team scope. The "us" in the original ask resolves to the current jacked user.
  • No background polling — Asana is queried only when /whats-next is actively invoked.
  • No generic adapter for Linear/Jira/Notion — Asana-specific guidance lives in the engine file. A second tool would grow a second optional section, not a polymorphic interface.
  • No fuzzy cross-linking beyond the literal GitHub URL in the task notes. We do not try to merge "GH #42: Fix login" with "Asana: Login broken".
  • No task-list caching — tasks are fetched fresh every run. The user GID and workspace list are persisted in the ## Asana Integration config block written by /jacked-setup whats-next, which is the single source of truth. To refresh, re-run the wizard.
  • No Asana-side label/tag filtering at the API level — Opus filters by reading task content. If config-driven label filters are needed later, they can be added then.

Failure modes

ScenarioBehavior
Wizard run but no access method available Write the install-hint block. Don't fail the setup — the user can still use /whats-next without Asana.
Runtime: ## Asana Integration missing from config Silently skip Step 3.5 (treat the same as opting out).
Runtime: Access: none in config Silently skip Step 3.5. Print one info line: Asana: not configured — run /jacked-setup whats-next to enable.
Runtime: configured access fails (auth expired, network down, MCP server hung) Print one warning line: Asana: not reachable (<reason>), skipping. Continue with the rest of /whats-next. Never abort the whole run.
Runtime: user GID changed (Asana account migration, edge case) If the cached GID returns 404, re-fetch it once with users/me and update the cache. Print one info line about the refresh.
Task with empty title or notes Drop it. There's no relevance signal to evaluate.

Open questions

  • Do we add a /jacked-setup whats-next --tune flag for interactive project picking (vs the default zero-touch "all"), or just expect the user to manually edit the config block? Current spec: zero-touch + manual edit; deferred until users ask for the picker.
  • Should the access-probe section live inside the standalone engine body too (so a cloner with no jacked installed can still benefit), or only in the wizard? Current spec: only in the wizard — the standalone command relies on the config-block decision the wizard made. Re-running the wizard is the way to refresh.
