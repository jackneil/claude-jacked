Intent

Agents add tests and do not retire them. The gates become slow, and a red gate costs one more full run. The owner wants one command that he can run in a repository folder. The command makes the test suite smaller and much faster, and it keeps the tests that protect real behavior. It must work in every place where jacked is installed, for Claude Code and for Codex.

The research is in 2026-11-25-test-suite-diet-research.html.

The owner said (2026-11-25 and 2026-11-26)My calls, each one open to a correction

  • The name: the skill /test-diet and the command group jacked tests.

  • When a gate is red, the recorder says if the same failing set was recorded before.

The facts that shape the design

  • Deletion alone does not make a gate fast. The best public pruning skill deleted about 400,000 test lines and claims no runtime saving.
  • The runner time is in the full and broad runs. In three repositories the test runner uses 11% to 35% of the summed agent time. Small pytest runs have a median of 5 to 11 seconds. A full run has a median of 9 to 17 minutes. The research did not measure the wait on the critical path of one goal, which can be much larger than the summed share.
  • A red gate is followed by one more run. 11% to 43% of the big runs are red. Most of them fail on 5 tests or fewer.
  • The same failure goes through the full gate again and again. In the Python data service, 82 red big runs show the failing files. One failing set returns in 13 big runs in 2 days, one in 12 big runs in 4 days, and one in 9 big runs in 3 days. Those three sets are 34 of the 82 runs. The three files that fail most often fail together in 19 of 19 runs, in days for which that repository's own notes name two of the three files and blame a stale local data file that git ignores. So the repeat failures there are incidents: a known failure, or the state of one checkout, that ran through the full gate many times. They are not a list of brittle tests.
  • The time is in a few files. In one repository 5.5% of the test files hold half of the time.
  • The causes differ by repository. A ranked list from other projects does not transfer. The skill must measure first.
  • Agents delete tests to get a green run: reported by others, not seen here. It is the most reported failure of agents in public reports. In the owner's five repositories, 2,524 commits of the last 120 days change test declarations. They add 30,417 declarations and remove 3,914. Only 28 commits have a net loss, and their subjects are reverts, splits of a pull request, removed features and one deliberate prune. This count reads declarations and commit subjects. It cannot see a weakened assertion or a new skip. The design must not give that failure a tool, and it does not need a hard check against it.
  • A cut of the count does not move the clock. The Python data service had a prune on 2026-11-24: 397 tests removed with evidence, about 2% of the suite. Its commit says that the cut does not move the wall clock and names the slow tests as the next work.
  • The machine is loaded. The load average was above 40 during this work, and 18 on 10 processors on 2026-11-26. One run before and one run after cannot show a saving of 10% to 20%. The owner does not want full gates of a large suite on this machine.

Goals, non-goals and anti-goals

Goals

  1. One command in a repository folder gives a smaller and faster suite on a branch, with a pull request and a measured result.
  2. The skill knows where the wait is without extra full runs.
  3. The skill retires tests of removed code, tests that assert a removed thing stays removed, tests that cannot fail, duplicates and change detectors. Each cut has evidence.
  4. The skill makes a slow test that has value cheaper. It does not delete it.
  5. The skill lowers the number of red gates. It gives a verdict on each failing set that returns in many red gates: the state of the checkout, a known failure that ran through the full gate again, a real guard, or a brittle test. A real guard stays and joins the targeted set, so that it fails before the gate. A brittle test gets a repair or a cut.
  6. The growth stops at its source: rules for a new test, a report of lost tests, a report of growth.
  7. A full gate does not have to run on the machine that the owner works on.

Non-goals

  • It does not write new tests, and it has no coverage target.
  • It is not a test selection service. It uses the related-test features that each runner has.
  • It does not need a mutation testing framework.
  • It does not merge. It does not change hosted CI without the owner's approval.
  • One repository for each run.

Anti-goals (the design fails if one of these occurs)

  • A deletion count is the measure of success.
  • A failing test is deleted, or the run cuts tests when the baseline is red.
  • A size or a time threshold decides that a test is junk.
  • A slow tier that no runner runs. That is a deletion with a different name.
  • A time budget turns a gate red because the machine is loaded.
  • A growth limit pushes an agent to delete adjacent tests to fit.
  • Transcript text, test output or failure text goes into a committed file.

Approaches

ApproachWhat it givesWhat it costs or misses
1. Install an existing pruning skill as a pack No build. Evidence-based pruning today. No time measurement, no lanes, no guard. It does not change the number or the length of the full runs.
2. The /test-diet skill alone Measure, repair the slow files and the repeat failures, prune with evidence, pull request. One extra full run before and one after in each repository. On a loaded machine those two runs prove little. No history of red gates on a machine that has no transcripts.
3. A gate recorder and the /test-diet skill (chosen) Each gate run records its durations, its failing tests and the identity of the tree. The skill reads that history. The saving is measured across real gates. A red gate says if its failing set was recorded before. The same record answers "did this exact tree pass already?". More to build: a command group in the jacked package and one line in each repository's gate.
4. Test selection only Fewer tests for each change. Targeted runs are already quick. Nothing becomes smaller.

Approach 3 is chosen because the measured problem is the number and the length of the full runs, and because a result that cannot be measured on a loaded machine cannot be trusted.

Part 1: the command group jacked tests

This is ordinary Python in the jacked package with ordinary tests. It does the mechanical work. The skill does the judgment. It is a command group and not a script beside the skill, because a script beside the skill needs an interpreter that the target repository may not have.

CommandWhat it does
runWraps the gate command: jacked tests run -- <gate command>. It measures the wall time, the load average, and the processor time of the child processes where the system gives it. It returns the exit code of the gate command without a change. Then it reads the JUnit XML of the run and adds one record to the local history: the identity of the tree, the runner, the kind of run (full or targeted), the counts, the duration of each file and each test, and the IDs of the failing tests. It keeps IDs, numbers and states only. It keeps no failure text. Each record names the machine that ran the gate. When the gate is red, run prints how many earlier records hold the same failing set, their dates and their trees, and if the base branch is one of them.
recordAdds a record from the JUnit XML of a run that was not wrapped, for example an artifact of hosted CI. A value that the file does not hold stays empty. It is not zero.
profilePrints where the time is: how many files hold half of the time, the slow files and tests, the setup share, and the difference between repeat runs of the same tree (the noise).
historyPrints the full runs, the red runs, the failing sets that return in many red runs with their dates and trees, and the full runs of a tree that had passed already.
seenAnswers: did this exact tree pass the full gate? It prints the record. A gate script or an agent can ask before it starts a full run. Its limit: the identity of a tree does not include files that git ignores. When a gate reads such files, a tree that passed can fail later with no change that seen can see.
idsTakes a list of the collected test IDs before and after a batch and compares both sides with the ledger. A removed ID, an added ID and a renamed ID must each have a ledger row. It knows the ID form of each runner.
ledgerChecks that each ledger row has the evidence that its kind needs. It refuses a delete row that has a missing field.
lossA report. It reads git only, so it needs no history and no test run. For the test files that a change touches, it counts the test declarations at the base and at the head. It prints the net change and the names of the removed declarations. A rename, a move and an edited parameter value do not change the count. It always exits 0. A reviewer or a gate log shows the line. It does not stop a change.

The history is in the common git directory of the clone, so all worktrees of one clone share it and git never commits it. The identity of a tree includes the changes that are not committed.

The ledger of a run is a file in docs/test-diet/ and is part of the pull request of that run. It records what was retired and why, so that an agent does not write the same test again. The commits of a batch carry a Tests-removed: trailer that names the ledger rows, as a record in the history of the repository.

A gate on a different machine

jacked tests run --on <label> -- <gate command> runs the gate command on a gate machine and records it here. The session and the history stay on the owner's machine. The gate machine needs git, Python, an SSH server and the tools of the repository. It does not need jacked. A gate machine can be a Linux, a macOS or a Windows system. The gate command of the repository owns its environment there: its database, its data files and its Python. The recorder applies these rules.

  • The tree must be the same. A gate machine runs a commit. run refuses a tree with changes that are not committed. It sends the commit over SSH to a clone on the gate machine and runs the gate in a new worktree of that commit, so no other work on that machine changes. The gate machine reports the commit that it ran and that its tree was clean. When the report does not match the commit that was sent, run makes no record and says why.
  • A lost connection is not a verdict. The gate runs detached on the gate machine and writes a log, its JUnit file and an exit marker. run waits for the marker and can attach again after a lost connection. With no marker there is no record, no pass and no failure. run returns the exit code that the marker holds.
  • Times of two machines are never compared. profile and the report compare records of one machine only. The baseline and the final gate of a diet run are on the same machine.
  • The address stays local. A committed file names the gate machine by a label. The host name, the address and the user are in a local file that git ignores.
  • One full gate at a time on a gate machine. run --on takes a lock on the gate machine before it starts a full gate. A second full gate waits and prints who holds the lock and since when. A lock whose holder is not alive is released. Without this lock, the sessions of several repositories move their pile-up from one machine to the other. This lock is my call.
  • The gate machine has its own work. The owner sets the number of workers and the priority for the gate there. run prints the processor load and the free memory of the gate machine before it starts the gate. It cannot stop work that other tools started there.
  • A rented machine needs the owner's account. A gate machine holds a clone of the repository and its test data. The owner names the account and approves the cost before a rented machine is used.

Part 2: the skill /test-diet

A skill directory with SKILL.md and a references/ folder. The text is guidance for a model. A name or a text pattern only nominates a test. The verdict comes from the assertions of the test and from evidence.

How it is startedWhat it does

/test-dietThe report, then the edits in batches on a branch, then a pull request. Its scope is the slow files and the tests that fail gate after gate.

Part 3: Codex must not start it by itself

Claude Code obeys disable-model-invocation. Codex does not read that key. Codex reads agents/openai.yaml in the skill directory: policy: allow_implicit_invocation: false (the default is true; read in the Codex documentation on 2026-11-25). The installer must write that file for each skill and each command that has the key. Today it does not, so review-animations and cleanup have the same defect. The fix covers all three.

What a run does

  1. Preflight. The run uses its own worktree. It never changes the branch of a checkout that other sessions use. It stops when the tree has changes that are not committed, or when it is inside an autonomous run. It reads the repository's rules for tests: a lock for one test session, a shared test database, ports. It obeys them in the scratch worktrees too. The refusal of an autonomous run is an instruction in the skill text: the skill stops when the session works on a /goal, /bhag, /loop or night-shift brief, or when a subagent starts it. jacked has no detector for this.
  2. Baseline. It uses the newest green full-gate record of the tree from the history. When no record exists, it runs the repository's full gate one time with JUnit output and records it. When the repository names a gate machine, each full gate of the run goes there, and the baseline is a record of that machine. When the baseline is red, the run gives a report only. It lists the failing tests as possible defects. A failing test is never a candidate.
  3. Where the wait is. From the history and the profile: the number of full runs, the share of red runs, the failing sets that return in many red runs, the full runs of a tree that had passed already, the slow files, the setup share, the collection and import time. For a failing set that returns, it runs those tests on the base branch in the same checkout. A failure there is the state of the checkout or a defect of the base, not a defect of the branch. It ranks the levers by measured seconds.
  4. The ledger, read-only. One row for each decision: Retain, Fix, Consolidate, Delete, Speed (make it cheaper) or Tier (move it to a slow lane). It works down the files from the largest measured share. The session's agent budget is the limit. The report says which share of the time it covered and what remains.
  5. Edits in batches by owner area. One commit for each batch: deletions that name the kept test, consolidations, speed repairs and tier marks. Speed repairs come from the measured cause: a shared fixture or one shared parse of the source tree, a call in the same process and not a subprocess, an injected clock, a rollback and not a commit, a smaller input.
  6. Proof for each batch. See What proves a cut.
  7. Preservation review. A separate read-only reviewer compares the deleted tests with the kept tests and looks for a contract that lost its only proof. Where the runner has a coverage tool, the run compares the covered production lines before and after. A line that lost its only test names a contract to restore. Coverage finds a lost line. It does not prove that a kept test checks the behavior. The number of reviewers stays inside the chain-of-command agent budget.
  8. Lanes. The run writes a Tests section into the repository's instruction file: how to run one file, the targeted set, the full gate with its record step, the label of the gate machine if there is one, and each one's measured time. It adds the rule for a red full gate: run the failed tests first. When the recorder says that the same failing set was recorded before, run those tests on the base branch in the same checkout before a repair. Repair, then run the full gate one more time. When the repository has a gate script, the run adds the wrapper, the JUnit output and the loss report there. When it has none, the run writes those commands into the Tests section. It creates a gate script only when the rules of the repository ask for one.
  9. The final gate. One full gate on the combined tree, recorded. The report compares the records: processor seconds and the sum of the call times, and the wall time with the load stated. A saving that is smaller than the noise is reported as not measurable. The report is an HTML file in docs/test-diet/ with numbers and IDs only. Then a pull request.

What proves a cut

Each cut names one of these proofs. The opinion of a reader is not a proof, and the agreement of several readers is not a proof.

KindThe claimThe proof
Dead targetThe test exercises code that does not exist: a removed import, a deleted subject file, a test that is skipped for good.The runner or the dead-code tool shows it. A check that the skip does not hide a real defect.
The pastThe test asserts that a removed thing stays removed.The assertion reads the definition of the thing itself, and no user depends on the absence. A test that guards a rule between two live structures is not this kind.
ShapeThe test cannot fail: no assertion, or an assertion that the types make always true.A script lists the members. One member still passes on a planted defect. A test stays in the batch only when each of its assertions has the shape.
DuplicateTwo tests have the same input and the same expected result. A script matches them. The kept copy exists and passes.
CoveredA kept test catches the same mistake.A planted defect in a scratch worktree fails the test to be deleted first. The same defect then fails the kept test. Coverage of the same lines only nominates the pair.
TestAll other cases: a change detector, a mock that supplies the asserted value, a copied list, a pin on source text.One test at a time: the full evidence fields below, a planted defect that the test does not catch, or a refactor that breaks it and changes no behavior.

The evidence fields of a row: the exact test and its location; the failure that it can detect; the callers of the covered code that are not tests; the stronger proof that remains, or why none is necessary; why the test exists (history); the code that the cut makes dead; the risk and the command that validates the cut. A row with a missing field is not ready.

Calibration on four tests of this repository whose names say "no longer", "retired" or "removed": one is a pure test of the past (a delete), one mixes a past assertion with a live length limit (a fix), one is an architecture rule with an incident behind it (keep, or move to a linter deny-list), and one guards a rule between two live structures (keep). A name finds candidates. It does not give the verdict.

Safety rules

  • Protected classes. Security, access and tenancy, health data and consent, money and billing, licenses, data integrity, migrations, public contracts, parity between two surfaces, tripwires, a test that a rule file of the repository cites, the only test of a public call, and tests that are the only proof that a shipped instruction text keeps a rule. These get Speed or Fix. A Delete needs a named approval in the pull request. Six of these classes (licenses, data integrity, parity, tripwires, cited by a rule file, the only test of a public call) come from the prune of 2026-11-24 in one of the owner's repositories.
  • Slow is not a reason to delete. A slow test gets a repair or a smaller input.
  • Tier needs a runner. The run refuses a Tier row unless the plan names the runner that runs the slow lane and how often. The full gate always runs the slow lane, so a Tier row does not make the full gate shorter. Its only use is a broad run during work.
  • IDs on both sides. After each batch, the removed, added and renamed test IDs must match the ledger. A collection error fails the check. The check uses the selection of the full gate, without parallel workers.
  • Order. The tests of a batch run alone, in random order, and with two workers when the runner can do that. A deleted test can hide the state that a kept test needs.
  • Side files. Files that name tests are updated in the same batch: shard and duration files, pin lists, coverage floors, count assertions.
  • Isolation. A speed repair must not weaken a tripwire that keeps tests away from the real machine.
  • No content in the history. The history and the report hold IDs, numbers and states. Agent transcripts are an optional local source for the history of one machine. Their text is never copied.

Acceptance criteria

  1. Install. jacked install puts the skill and its references into ~/.claude/skills/test-diet and into the Codex skills folder. The dashboard toggle and the uninstall work. Claude Code does not list the skill for the model. Codex gets a policy file that forbids implicit invocation, for this skill and for each other skill or command that has disable-model-invocation.
  2. Record and profile. Given JUnit files captured from real runs of pytest, Vitest, Jest, Playwright, gotestsum and cargo-nextest, record and profile give the same normalized fields, with the correct unit for each runner. The sample files come from real runs. They are not written by hand.
  3. IDs. The check fails on a removal that has no ledger row. It fails when a delete row's test is still collected. It passes on a consolidation that renames tests when the ledger has the map. A line shift in a Playwright file is not a change. A collection error fails.
  4. Ledger. A delete row with a missing evidence field is refused.
  5. Loss report. For a change that lowers the net count of test declarations, loss prints the net change and the removed names. A rename, a move to a different file and an edited parameter value print no loss. It exits 0 in each case.
  6. Wrapper. jacked tests run returns the exit code of the command that it wraps, for a pass and for a failure.
  7. Repeat failure. A red run whose failing set is in two earlier records prints those records, and says when the base branch is one of them. A red run with a new failing set prints no such line.
  8. Gate machine. run --on records a gate only when the commit that the gate machine reports is the commit that was sent. A run with no exit marker makes no record. profile does not compare the times of two machines. A second full gate for one gate machine waits for the first. No committed file holds a host name or an address. The proof uses a real second machine, not a second folder of one machine. It covers a Windows gate machine and a Linux gate machine.
  9. Refusals. A tree with changes that are not committed stops the run. A red baseline gives a report only. A failing test is never in a delete row. The skill text refuses an autonomous run. That is an instruction, and the live proof tries it one time inside a brief.
  10. Privacy. The history holds no failure text. record writes to no tracked file.
  11. Live proof, this repository. A full /test-diet run on claude-jacked in a worktree: recorded gates before and after, the ledger, the report and its own pull request.
  12. Live proof, the Python data service (the owner's pick, 2026-11-26). No full gate of this proof runs on the owner's laptop. The first milestone is one green recorded full gate on the gate machine. A red baseline there stops the edit phase, by the rule above. Then: the record step in its gate, a report from real recorded gates, and the edit phase, with the rules of that repository for its test database obeyed. That repository had a prune of redundant tests on 2026-11-24, so this proof is about seconds: the slow files and the failing sets that return. The baseline and the final gate are records of the same machine.
  13. The shipped text. The approved changes are in, the pins are updated, the full suite is green, and the counts in the README and in the reference are correct.
