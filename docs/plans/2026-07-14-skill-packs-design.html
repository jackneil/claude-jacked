Goal

Let a jacked user opt in to curated collections of third-party skills ("skill packs") as part of jacked install and from the dashboard, without jacked vendoring any third-party content. Upstream repos stay the single source of truth; jacked orchestrates install, update, verification, and removal through the vercel-labs npx skills CLI (skills.sh), which is also the upstream-recommended installer for the repos in question.

Context: Jack evaluated three third-party skill repos on 2026-07-14 (marketingskills scored 47 skills via 9-agent review; emilkowalski/skills diffed against jacked's vendored copies; first-customer-finder found to be absorbed into marketingskills' prospecting skill with credit). Explicit direction: no vendored clones that drift out of sync; jacked manages the install but the upstream repo and its own manager coordinate the skills. Opt-in is a CLI flag plus a dashboard toggle.

Empirically verified skills-CLI behavior (sandbox, 2026-07-14, CLI v1.5.17)

  • npx -y skills add owner/repo --skill a b -g -y -a claude-code codex puts the canonical full skill directory at ~/.agents/skills/<name>/ and a relative symlink at ~/.claude/skills/<name>.
  • Lockfile ~/.agents/.skill-lock.json (v3): per-skill source, sourceUrl, skillFolderHash, timestamps. Multiple source repos coexist.
  • npx -y skills update -g -y refreshes all globally installed skills from their sources; npx -y skills remove name -g -y removes canonical dir, symlink, and lock entry.
  • Gotcha: requesting a nonexistent skill name exits 0 and installs nothing. Exit codes cannot be trusted; every operation is verified on disk afterward.
  • The CLI detects agent sessions and runs non-interactively; -y plus explicit -a makes runs deterministic. skills.sh runs its own per-skill security scan during install.

Architecture

One new core module (jacked/packs.py) owns registry parsing, enablement state, subprocess orchestration of the skills CLI, and post-operation disk verification. The CLI layer and the dashboard API are thin consumers of that module.

Flows

  • Enable: persist intent in state file, run skills add with the pack's curated --skill list, verify every expected skill exists at both destinations, report loudly on misses.
  • Every jacked install: after the main install and Codex pass, refresh enabled packs (skills update + verify + one repair attempt for missing skills). Missing npx: loud warning, never fails the main install.
  • Disable / uninstall: remove only skills whose lockfile entry matches the pack's source; anything same-named from another source is skipped and reported. jacked uninstall removes all enabled packs' skills and the state file.
  • Dashboard: GET /api/packs for status (per-skill installed/source-ok/updated-at), PUT /api/packs/{name} to toggle; the slow npx work runs off the event loop with a pending state in the UI.

Safety rails

  • Verify, never trust exit codes: the CLI exits 0 for unknown skill names, so every add/update/remove is verified against the filesystem and failures name the exact skills (upstream renames surface immediately instead of installing nothing silently).
  • Source-checked removal: a skill is only removed when the lockfile says it came from the pack's repo. Same-named skills from other sources are never touched. jacked never deletes skill directories itself; all removal goes through the skills CLI.
  • No collision with jacked-shipped skills: a test asserts no pack skill name matches any directory in jacked/data/skills/, so a pack can never shadow a vendored skill.
  • Manifest isolation: pack skills never enter jacked's install manifest, so manifest pruning cannot remove them; pack state lives in its own ~/.claude/jacked-packs.json.
  • Trust boundary: enabling a pack means trusting the upstream repo's main branch at install/update time (explicitly accepted trade-off). Only skills/ content is installed; upstream AGENTS.md and tools/ never reach the machine. skills.sh adds its own scan during install.
  • Degradation: no Node/npx means packs are unavailable with a loud, actionable message; the core jacked install is never blocked or failed by pack machinery.

Testing

  • Fake-npx shim (scenario-driven executable) emulates verified CLI behavior including the silent-skip rc=0 gotcha, non-zero exits, and hangs; tests prove the disk verification catches what exit codes miss.
  • Registry validation: unique skill names across packs, no collision with vendored skills, malformed JSON tolerated loudly.
  • State: atomic writes, corrupt-file tolerance, round-trip.
  • Removal safety: foreign-source and unlocked skills are skipped, own-source removed, verified gone.
  • CLI + API layers tested with the packs module mocked; dashboard section browser-verified on a scratch-HOME instance before merge.
